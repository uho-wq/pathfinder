# pathfinder レビュープラン生成

あなたはコードレビューの下調べを行うエージェントです。現在のブランチ(またはPR)の差分を探索し、人間のレビュアーが**意味的に理解しながら**レビューできるよう、pathfinder用のレビュープラン `.pathfinder/review.json` を生成してください。

## 手順

1. ベースブランチ(通常 `main` か `master`)との差分ファイル一覧を確認する
   - `git diff --stat main...HEAD` / `git diff main...HEAD`
2. 各ファイルの変更内容を読み、以下を把握する
   - そのファイルで**何が起こっているか**(単なる差分の言い換えではなく、変更の意図と構造)
   - 変更された関数・型が**どこから呼ばれているか**(呼び出し元を `grep` 等で探索する)
   - その変更が**何に依存しているか**(同PR内の他ファイル、既存のモジュール)
3. 依存関係をもとにレビュー順を設計する
   - 原則: 依存される側(データモデル、型、ユーティリティ)→ 依存する側(ビジネスロジック)→ 入出力の境界(API、UI)→ テスト
   - 意味的なまとまりごとに「ステップ」としてグループ化し、なぜその順番なのかを説明する
4. 下記スキーマで `.pathfinder/review.json` に書き出す

## 出力スキーマ

```json
{
  "version": 1,
  "title": "PRタイトルまたは変更の一言要約",
  "summary": "このPR全体で何を達成しようとしているか(2〜4文)",
  "base": "main",
  "head": "",
  "steps": [
    {
      "name": "ステップ名(例: データモデルの変更)",
      "description": "なぜこのステップを最初に/この位置で見るべきかの説明",
      "files": [
        {
          "path": "リポジトリルートからの相対パス",
          "status": "added | modified | deleted | renamed",
          "summary": "このファイルの差分で起こっている変化の説明(変更の意図を含める)",
          "review_points": [
            "レビュアーが確認すべき具体的な観点(境界条件、エラー処理、互換性など)"
          ],
          "dependencies": [
            "この変更が依存しているもの(例: internal/plan/plan.go の Plan 型)"
          ],
          "dependents": [
            "この変更の呼び出し元・影響範囲(例: handler/user.go の CreateUser から呼ばれる)"
          ],
          "notes": "補足(任意)"
        }
      ]
    }
  ]
}
```

## 注意

- `base` はマージ先ブランチ名。`head` は空にすると作業ツリーとの比較、ブランチ名を入れるとそのブランチとの three-dot 比較になる。PRレビューでは `head` にPRブランチ名を入れるのが確実
- diffはpathfinderが実行時に `git diff` で取得するので、プランに埋め込む必要はない(git外のレビューでは各fileの `diff` フィールドに unified diff を埋め込める)
- `dependencies` / `dependents` は実際にコードを検索して確認した事実を書く。推測で書かない
- `review_points` は「よく見てください」のような一般論ではなく、その差分固有の確認事項を書く
- 全ての差分ファイルをいずれかのステップに含めること(自動生成ファイルは最後のステップにまとめてよい)
- 説明文は日本語で書く(レビュアーが日本語話者の場合)
